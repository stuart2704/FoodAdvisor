# Manual restaurant grid crawl

This crawler is **not scheduled** and does not run with the API server. It cannot recover the original database. It creates new listings using Google Places Nearby Search, which may incur charges. Each point returns up to 10 restaurants, not all restaurants in a city. It stores name, address, city, mapped region/country, actual place coordinates, rating, review count, cuisine tags derived from Places types (or a name-only keyword fallback), price level, canonical Place ID, and Maps URL in the existing table. Missing Places fields stay null or empty rather than being invented. Amenity keywords are available in code, but no amenities are inferred from a Maps search page or restaurant name.

The additive `lib/db/migrations/0014_restaurant_review_count.sql`, `lib/db/migrations/0015_restaurant_classification_candidates.sql`, and `lib/db/migrations/0016_restaurant_updated_at.sql` columns must be present on the database the API uses before starting the updated API or running the confirmed crawl. New crawled listings copy their cuisine tags into `cuisines`; `amenities` stays null until a trustworthy venue-specific source is available. Existing cuisine and amenity values are not backfilled. The `updated_at` column defaults to the insertion time for new rows; the migration leaves older rows null so they are eligible for an initial refresh. On a verified refresh, the crawler sets `updated_at` explicitly. If an earlier version of the migration already stamped historical rows, review and clear only those artificial timestamps before relying on the 60-day rule.

The included `coordinates.json` contains only the 20 points provided for London and New York City. It is a partial grid: no other city points have been invented. To expand it, add verified `[latitude, longitude]` pairs:

`src/lib/regionSchedule.ts` orders supplied points as Europe, North America, Asia, Middle East, Africa, then South America. Missing regions have no points and are not invented. This order does not run a daily schedule or rotate regions; the validated progress file resumes by point index. Do not advance a separate region index after a failed or partial crawl. Manual runs log `region_start` and `region_end` with points completed in that run and a `completed` flag; an interrupted region is not reported as completed. No weekly-cycle event is emitted without a completed, persistent rotation.

```json
{
  "europe": {
    "london": [[51.5074, -0.1278]],
    "paris": [[48.8566, 2.3522]]
  },
  "north_america": {
    "new_york": [[40.7128, -74.006]]
  }
}
```

Only cities present in the application's verified region map are accepted. The example above is illustrative, not the missing original grid.

From the project root, first preview the plan without connecting to a database or making an API call:

```bash
pnpm --filter api-server exec tsx src/scripts/gridCrawl.ts --grid coordinates.json --state grid-progress.json --monthly-budget-cents 3000
```

To run intentionally, add `--confirm` to the same command. The state path must be writable and **persistent across runs**; keep the original grid file unchanged. A changed grid or invalid progress fails closed rather than restarting at point zero. The script processes at most 50 attempted points per UTC day, delays 15 seconds between calls, and resumes from the next completed point. Each call reserves a conservative estimated 50 pence in the existing import ledger **before** contacting Google. Manual runs require an explicit estimated monthly budget of 50–3000 pence; the script checks both that budget and a 60-request ceiling against monthly import-ledger reservations before each request. These are **not** guaranteed invoice caps: actual Google pricing and other usage may differ, so use a provider-side quota/budget too. Failed or uncertain requests stop the run without advancing the point; inspect the result before retrying because retrying could be charged again. New Place IDs are inserted. Existing listings are refreshed when more than 60 days old, when a verified incoming rating differs by more than 0.3, when a verified review count rises by more than 50, or when incoming verified data can fill a missing address, cuisine, price level, or website. These rules apply to Places results from a manual grid search; they do not schedule another search or restart a completed grid. The refresh only writes non-empty, verified Places name/address/website/price and valid rating/review count/structured cuisine; it preserves city, country, coordinates, region, Maps URL, existing amenity, phone and type fields, and all claim/outreach data. Missing provider values never clear existing data. Missing amenities and public phone are reported as gaps, not used to trigger an unchanged refresh; Nearby Search does not supply them and owner contact information is private. Never commit real credentials or progress files to source control.

The `daily_summary` log entry counts work in the **current confirmed run** (`period: "this_run"`), not combined totals across multiple invocations on the same day. It includes completed grid points, inserted and refreshed restaurants, recent-listing skips, and an error count if the run stops with an exception.

After a grid request is reserved, `budget_used` reports the remaining UTC-day request attempts from the persisted progress count. If the 50-attempt allowance runs out while grid points remain, `budget_exhausted` is emitted. Both events concern request attempts, not the separate estimated monthly money budget. Restaurant priority is determined from the Places result after the request; skipping low-priority database updates at that point would not save an API call.
`daily_budget_summary` reports the persisted `used` and `remaining` attempt allowance across confirmed invocations on the current UTC day. It is distinct from `daily_summary`, whose restaurant counters cover only the current run.

`budget_status` reports attempts used and remaining, plus a proposed five-request emergency reserve (`reserve_target: 5`, `reserve_enforced: false`). The reserve does not yet hold back any requests: the crawler cannot identify a highest-priority grid point before fetching Places results. It does not emit `skip_non_critical` or claim a deep crawl occurred.

The additive `crawler_progress` table has a single seeded row (`id = 1`) and is available for future database-backed resumption. Reads and position updates must target that row; an unrestricted `LIMIT 1` or `UPDATE` is unsafe. Saved position indexes are interpreted as the **next unprocessed point**, not the point just completed. A read-only resolver follows the explicit region order, rejects invalid or absent coordinates, and returns no next point at the end instead of wrapping to another paid cycle. **The manual crawler does not use this table yet**: its validated `--state` file remains authoritative. The table lacks the grid hash and UTC-day attempt state needed to replace that file without risking repeated billable requests. `paid_requests` is not maintained by the current crawler, and the seeded `last_run` default is row creation time, not proof of a completed crawl. For an external production database, apply the migration only after confirming the correct target; publishing the app does not migrate an external database automatically.

The optional database counters `paid_requests_today` and `paid_requests_month` start at zero, and `last_paid_reset` defaults to the current **UTC** date. These are storage fields only: no process currently increments or resets them. Before they can enforce any limit, a paid request must be reserved atomically across concurrent runners, with UTC day/month rollover and uncertain failures handled explicitly. The estimated monthly cost ledger and provider-side billing controls remain separate from request counts.

`crawl_priority` classifies existing restaurants **after** the paid Nearby result returns: `DEEP=3`, `RECOVERY=2`, `STALE=1`, `FRESH=0`. `DEEP` follows the existing eligibility check and never triggers another fetch; it can include missing amenities. `RECOVERY` requires a missing field the incoming verified result can actually fill, rather than missing phone/amenities alone. Staleness/update eligibility still controls writes independently of the priority label; this classification does not alter which grid points are searched.

The 40% (24 requests), 70% (42), and 90% (54) priority thresholds are a tested policy **for future separately billable work only**; at 60 requests all paid work must stop. No such deep fetch exists yet. `budget_priority` logs a restaurant's classification and the monthly import-ledger count including the grid request that found it. It does not emit skip events or drop results after paying for a grid search, and it does not read the unused `paid_requests_month` field.

The database row also defaults to `cycle_number = 1` and `cycle_completed = false`. These fields are **not maintained by the manual crawler**. Its file cursor stops at the end of the grid; it does not reset to point zero or start another paid cycle. Marking a cycle complete requires proof that the last validated grid point and all its writes finished; starting another requires an explicitly controlled schedule, grid identity, atomic reservations, and concurrency protection. The existing `daily_summary` is authoritative for completed work; a `cycle_summary` using the currently unused DB paid counters would be misleading.

City entries may remain arrays of `[latitude, longitude]` pairs, or use `{ "points": [[lat, lng]], "popularity": 0.8, "density": 0.6, "missing_fields_rate": 0.3 }`. All three planning scores are required numbers between 0 and 1. Their informational city weight is `0.4 × popularity + 0.3 × density + 0.3 × missing_fields_rate`; it does not change paid request order or allocate spending. Editing scores changes the grid file hash, so a crawl with existing file progress fails closed until that progress is reviewed rather than silently resuming a different plan.

An informational adaptive allowance can be calculated as `floor(floor(60 / validated point count) × (0.5 + city weight))`; for 20 points and the example Cardiff scores, this is 3. It is not enforced: the crawler still makes at most one grid request per point and checks the monthly estimated-cost ledger before it. There is no `city_metadata` table or defined source/calculation for live city popularity, density, or missing-field rates, and the database cycle/monthly counters are not maintained. An `adaptive_budget` event that claims `paid_requests_month - paid_requests_last_point` would therefore report false usage and is not emitted.

Separate region-level planning scores can be evaluated as `0.4 × popularity + 0.3 × density + 0.2 × missing_fields_rate + 0.1 × stale_rate`, with each input constrained to 0–1. The sample Europe and Asia values yield 0.71 and 0.67 respectively. This pure calculation does not parse a score-only JSON object as crawl coordinates, change the region schedule, or enable paid requests.
`computeRegionWeight` is another name for this same validated region score; it does not assign a monetary or request budget.

Prospective region intervals are computed as `round(7 - priority × (7 - 1))`: a priority of 0 gives 7 days, 1 gives 1 day, and both sample region scores round to 3 days. This is a pure planning calculation. There is no per-region last-crawl history or automatic paid scheduler; these intervals do not start a new crawl cycle.

`crawler_progress.next_region_run` defaults to `NULL` and `region_interval` defaults to 3 days (allowed range 1–7). Both are storage-only. This singleton row cannot independently hold each region's due date, and neither field is used to choose a region or initiate a paid request.

`region_budget` and `region_budget_used` also default to zero and cannot be negative. They are storage-only on the singleton row; the supplied Europe score example can be evaluated by the pure region-priority function, but it does not establish a region budget or maintain these counters. The confirmed crawler continues to check the estimated monthly import ledger before each Google request, not these fields.

A read-only allocation calculation can divide the **60-request estimated monthly ceiling** across supplied regions by their validated weights, flooring each share. For the sample Europe (0.71) and Asia (0.67) scores it plans 30 and 29 requests; the one-request rounding remainder stays unallocated. This does not update `crawler_progress`: it has only a singleton row and no `region_name` column, so an `UPDATE ... WHERE region_name = ...` cannot persist separate region budgets. Allocations also do not replace the global estimated-money check or provider-side billing controls.

A future per-region exhaustion decision requires a configured positive region budget and an authoritative per-region used count; zero/zero is an unconfigured error, not `region_budget_exceeded`. No `region_budget_exceeded` event or region skip is emitted by the manual crawler because its singleton region counters are unused and cannot identify which region incurred charges.

Do not increment `region_budget_used` with `WHERE region_name = ...` on `crawler_progress` (there is no `region_name`), or reset it with an unrestricted `UPDATE`. A future per-region paid request must reserve its usage atomically before calling the provider, scoped to the correct region and UTC month. Completing a grid cycle or reaching a region due date is not a monthly billing reset; preserve reservations and ledger history until the proper rollover.

For the same reason, no `region_budget_status` log is emitted from the singleton row. Its zero defaults cannot truthfully describe a named region's budget, used requests, or remaining allowance.

`city_progress` is an empty table for future `(region_name, city_name)` budget records, with unique city identity and nonnegative `city_budget`/`city_budget_used` defaults of zero. No city budgets are assigned or spent by the crawler. City-budget scoring uses four factors (popularity 40%, density 30%, missing-fields rate 20%, stale rate 10%): the Cardiff sample scores 0.58. This is separate from the grid-point city's earlier three-factor informational weight of 0.59. Reading the singleton `progress.region_budget` does not supply a per-city or per-region allocation.

A pure city-share planner floors each city's four-factor weight divided by the sum of **all listed cities' weights**, multiplied by an explicit positive region allowance of at most 60 estimated requests. It rejects missing city scores, duplicate city names, a zero total weight, and the singleton's unconfigured zero region allowance. Rounding remainders stay unassigned. It does not upsert `city_progress`: only Cardiff scores are provided, and the singleton does not hold an authoritative per-region allowance.

The future city-budget exhaustion comparison rejects an unconfigured zero budget instead of emitting `city_budget_exceeded` for 0/0. No such skip or `city_budget_used` increment is active. A separate read and `UPDATE city_progress SET city_budget_used = city_budget_used + 1` can race and does not guarantee a row was found; recording it after Google replies is too late. A future paid request must atomically reserve its city, region, and global monthly usage before contacting Google, retain uncertain reservations, and use a month-scoped source of truth.

Do not clear all `city_budget_used` values with an unrestricted `UPDATE`; a grid cycle is not a monthly billing rollover, and erasing reservations could permit duplicate spending. No `city_budget_status` event is emitted while city rows are empty and their usage is not maintained. Once per-city reservations exist, status should be read by the exact `(region_name, city_name)` and month, not copied from the singleton progress row.

`paid_requests_last_point` defaults to zero as a prospective monthly-request baseline captured on entry to a grid point. It is not updated by the manual crawler. A proposed `paid_requests_month - paid_requests_last_point` smoothing rule must not be applied to the current Nearby result loop: it would run after the paid search and drop data without refunding the request. Any future per-point limit must be checked and reserved before a separately billable request, on the same authoritative cursor and monthly ledger.

On a confirmed manual run with grid points remaining, `paid_budget_status` reports the **pre-request** monthly call count and estimated spend from the import ledger, not the unused `crawler_progress` counters. `remaining_requests` reflects whichever is lower: the request ceiling or the number of estimated 50-pence requests left under the run's explicitly supplied budget. No monthly reset is performed on the database counters.
